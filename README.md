# promo_monitor

Мониторинг промоакций и welcome-бонусов конкурентов: раз в сутки (08:00)
проверяет заданные страницы, сравнивает с прошлым снапшотом, формирует
Excel/HTML-отчёт и (опционально) отправляет его на почту. Работает локально
на ПК через Планировщик заданий Windows — при необходимости позже можно
перенести на VPS или добавить другой канал уведомлений.

Статус "Промяна в промоцията" в отчётах держится видимым 24 часа с момента
реального изменения, а не только на том единственном прогоне, где оно было
найдено (см. `notify/formatting.py::display_status`) — при проверке раз в
сутки иначе легко открыть отчёт уже после того, как статус тихо вернулся в
"Без промяна", и не заметить, что изменение вообще было. Колонка/строка
"Последна промяна" показывает точную дату независимо от того, активен бейдж
или уже погас.

Ограничения, которые бот соблюдает: не создаёт аккаунты и не обходит
верификацию, использует только вручную сохранённые сессии/cookies для
закрытых страниц, уважает `robots.txt`, не пытается решать капчи или обходить
антибот-защиту (Cloudflare/DataDome/PerimeterX/hCaptcha) — такие сайты
помечаются `blocked_by_antibot` и исключаются из автоматической проверки.

## Установка

```bash
pip install -r requirements.txt
playwright install chromium
```

## Настройка

1. Скопируйте `config/.env.example` в `config/.env` и заполните SMTP-данные
   для отправки отчёта на почту (`SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD`,
   `EMAIL_FROM`, `EMAIL_TO`). Для Gmail — `SMTP_HOST=smtp.gmail.com`,
   `SMTP_PORT=587`, пароль — app password аккаунта, а не обычный.
   Если SMTP не заполнен — письмо просто не отправляется, отчёт всё равно
   сохраняется в `reports/`.
2. Для каждого сайта с `access: auth_required` — `<PREFIX>_COOKIES`
   (рекомендуется) либо `<PREFIX>_LOGIN`/`<PREFIX>_PASSWORD`. Аккаунт на
   сайте конкурента заводится вручную человеком заранее; автоматический
   логин через форму в MVP не реализован — проще один раз выгрузить cookies
   залогиненной сессии браузера.
3. Отредактируйте `config/sites.yaml`: до ~10 сайтов, для каждого — `url`,
   `access` (`public`/`auth_required`), `render` (`static`/`js`) и CSS-`selector`
   промо-блока (индивидуально под вёрстку сайта).

`config/.env` не коммитится в git (см. `.gitignore`).

## Запуск

Один прогон по всем сайтам:

```bash
python main.py
```

В проде это запускает Планировщик заданий Windows (`run_daily.bat`) —
задача `PromoMonitorDaily` настроена на запуск **раз в сутки, в 08:00**.
Задача — на логон-типе S4U (без пароля), поэтому стартует сама, даже если
никто не залогинен на ПК (см. `Principal.LogonType` в свойствах задачи).
Изменить время запуска (нужен elevated PowerShell — S4U-задачи требует прав
администратора даже для смены триггера):

```powershell
$t = New-ScheduledTaskTrigger -Daily -At "08:00"
Set-ScheduledTask -TaskName "PromoMonitorDaily" -Trigger $t
```

Есть и альтернативный режим — долгоживущий процесс с внутренним
планировщиком (ежедневно в заданное время, без Планировщика Windows):

```bash
python main.py --schedule --hour 6 --minute 0
```

`--stagger-seconds` (по умолчанию 300 = 5 мин) — пауза между проверками
сайтов внутри одного прогона, чтобы не бить все сайты одновременно.

## Отчёт и письмо

- После каждого прогона создаётся `reports/promo_report_<дата_время>.xlsx` со
  строкой на каждый сайт: статус, было/стало (или причина ошибки), ссылка,
  время.
- В HTML-отчёте (`reports/latest.html`, он же публичная страница) каждая
  акция показана целиком — текст не обрезается — и по клику открывает
  информацию об акции. Что именно открывается, зависит от сайта:
  - **Inbet, Winbet, Sesame** — карточка в разметке это `<a>` с адресом самой
    акции (`/promotions/<раздел>/<slug>?tab=conditions`);
  - **MrBit, AdmiralBet, efbet** — в разметке ссылки нет (карточка открывается
    JS-обработчиком), но страница получает список акций вместе с адресами из
    своего API. Playwright перехватывает этот ответ при загрузке (`link_api` в
    `sites.yaml`, разборы — `scraper/link_apis.py`): ни одного лишнего запроса к
    сайту, никаких кликов по сотне карточек. Правила сборки адресов сверены с
    реальными кликами;
  - **8888.bg** — карточка акции это popup **без своего URL**: адрес не меняется,
    ни один из 14 проверенных вариантов адреса, JS сайта и sitemap его не
    открывают, поэтому ссылки на неё на самом сайте не существует. Бот берёт текст
    её правил и условий тем же запросом, что делает сайт при клике (`card_pages` в
    `sites.yaml`, `scraper/details.py`; проверяется robots.txt, запросы
    последовательные, с паузой) и собирает из него обычную HTML-страницу
    (`notify/card_page.py`, файлы в `docs/promo/`): настоящий текст, который можно
    читать и копировать, настоящие ссылки сайта из самой карточки (у «Стартов
    казино/спорт пакет» это их страницы `/promo/bonus_casino`, `/promo/bonus_sport`)
    и кнопка на сайт. В имени файла — хэш содержимого, поэтому страница
    пересоздаётся, только когда акция изменилась. У акции без отдельной карточки
    (LIVE-акция, единственная кнопка которой — «Вход») страница из текста самой
    карточки, с пометкой об этом;
  - **Betano** — ссылок на акции нет совсем: адреса из его API ведут на главную с
    «панелью» (для посетителя это просто список матчей) или в раздел за логином, и
    выдавать их за ссылки на акции было бы неправдой. Кроме того, сайт при
    тестовых заходах показывает «Access is temporarily restricted» — его защита от
    автоматизации, которую проект не обходит;
  - всё, для чего точного адреса нет, ведёт на страницу промоций сайта (при
    наведении подсказка «Към страницата с промоциите на сайта») и **выводится
    в конце списка** — наверху те акции, по клику на которые открывается именно
    она сама.

  Сайты с `report_bottom: true` в `sites.yaml` (8888.bg, Betano — открыть саму
  акцию по клику нельзя) выводятся в самом низу таблицы.

  Ссылки лежат в базе рядом со снапшотом (`links_json`), но в хэш для
  сравнения не входят — смена одного URL не считается изменением акции.
- Если в `.env` настроен SMTP — отчёт уходит письмом с этим файлом во
  вложении. По умолчанию письмо уходит после каждого прогона, даже если
  изменений нет; поставьте `REPORT_ONLY_ON_CHANGES=true`, если нужно письмо
  только при реальных изменениях/ошибках.

## Логи и хранилище

- Логи прогонов: `logs/monitor.log` (успех / изменение / ошибка мониторинга —
  отдельно от "изменилась акция").
- Снапшоты: SQLite `storage/promo_monitor.db`, таблица `snapshots`.

## Если сайт сломался или недоступен

- Селектор перестал находить блок (редизайн) → статус `no_selector_match` в
  отчёте — это не считается изменением акции, нужно проверить селектор вручную.
- Сайт отдал капчу/challenge-страницу → статус `blocked_by_antibot`, сайт
  исключается из мониторинга до ручной проверки; бот не пытается её обойти.
- Сетевая ошибка/таймаут (30 сек, 1 повтор) → статус `error`.

Ошибка на одном сайте не прерывает прогон остальных.

## Перенос на VPS (позже)

Локально это просто `python main.py` по расписанию (Планировщик заданий
Windows или `python main.py --schedule` как процесс, который не закрывают).
При переносе на сервер — тот же код: cron раз в сутки вызывает
`python main.py`, либо systemd unit с `python main.py --schedule`. Секреты
переносятся вместе с `.env` (не через git).
